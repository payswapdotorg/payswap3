## Q1 — Where the Rail Authority's protocol state lives

Ruling: RailAdapter registry state and the RailOperation lifecycle (AUTHORIZED→SUBMITTED→PENDING | terminal(CONFIRMED | FAILED | UNKNOWN)) are protocol-owned authoritative state, persisted under the authoritative-state-store's persistence convention and transitioned only through the single-writer path (protocol-gateway admission → durable command path → transition-runtime), with the external-rail-adapters component — and RTN-004's simulated rails — as pure transmission and reporting that never mutate protocol state; the proposal's assumption is confirmed.

Spec grounds: Ruled by precedence — frozen architecture v0.1 first, the registry second, deployment contracts third.

- spec/architecture/v0.1/rails-adapters-reconciliation.md, Area 13, Owning authority: "Rail Adapter Authority (protocol layer, area 13) owns adapter registry and operation lifecycle. The external rail is an untrusted reporter: its data is evidence, not protocol truth."
- Same file, Area 13, Purpose: "Adapters translate protocol-authorized instructions into external actions and report external results back — including UNKNOWN — without ever owning protocol financial state."
- Same file, Area 13, RailOperation: "UNKNOWN: submission outcome cannot be determined (timeout, connection loss, ambiguous rail response). This is a durable state; adapters MUST NOT resolve UNKNOWN by re-submission." — a durable protocol state cannot live in a component that hosts no authority.
- Same file, Area 13, Boundaries: "Adapters never write obligation, settlement, or finality state; they report to area 12." / "Adapters never hold protocol balances; the external rail's balance view is an external claim to be reconciled, not truth (GC-4)."
- Same file, Area 14, INV-14-2: "a case's terminal resolution transitions the originating rail operation exactly once; duplicate resolutions are rejected by case id" — the operation is transitioned by protocol resolution, not by the adapter.
- spec/registry/protocol-registry.json, A13: owningAuthority "Rail Authority"; primaryObjects "RailAdapter", "RailOperation", "RailReceipt", "AdapterStatusQuery" — protocol objects of a protocol area.
- spec/deployment/topology.md, Runtime ownership of protocol authorities: "There is exactly one protocol-command admission point (protocol-gateway) and exactly one authoritative-state writer (transition-runtime)." — the adapters component is excluded from the protocol-authority hosting list in the same section.
- deploy/contracts/components.json, external-rail-adapters: "authority_hosted": "none — the only component that transmits to external rails; transmits exclusively protocol-authorized outputs and cannot originate or alter financial decisions; holds rail credentials and fails closed when they are absent; ingests external evidence into evidence-object-store" — consistent once read as transmission-only; it contradicts nothing in v0.1, because the authority's state lives in the protocol-owned store, not in the transmission component.
- deploy/contracts/components.json, authoritative-state-store: "protocol-owned authoritative state (identity, accounting, reservations, obligations, settlement and finality records) on deployment-owned persistence infrastructure; mutated only by transition-runtime through protocol-owned transitions — no other layer may mutate it directly" — the parenthetical is illustrative, not exhaustive; v0.1 README §9: "This directory defines semantics only; it intentionally prescribes no implementation, storage, or service decomposition," so the frozen text does not confine where protocol state persists — the deployment topology's single-writer rule does.
- Corroboration: GC-5 (spec/architecture/v0.1/README.md): "Each writes exactly one evidence record (area 15)... committed atomically with the state transition" — RailOperation transitions are consequential (they authorize external effects, per INV-13-1), so they require the A15 synchronous commit coupling ("an operation is not committed until its record is written. A failed write fails the operation"), which is realized only on the single-writer path (RTN-011).

Conflict statement: v0.1 Area 13's owning-authority sentence and components.json's "authority_hosted: none" for external-rail-adapters appear to conflict. Ruled in the stated order: frozen v0.1 first (the Rail Adapter Authority owns the lifecycle), the registry second (A13 objects are protocol objects), deployment contracts third (the adapter component hosts no authority — it transmits; its marker text "FUTURE-WORK: protocol adapter semantics per dependency graph WORK-001..WORK-033" is exactly the protocol-owned semantics this wave materializes elsewhere). The conflict dissolves; nothing is altered.

Scope impact: Confirm RTN-004 as scoped, with one precision added: the rails/ surface implements the A13/A14 state machines as authority state under the RTN-001 per-domain persistence convention, and the adapter interface (simulated now, real under DEP-005) is strictly transmission-and-reporting — no code path in the adapter interface creates or mutates RailOperation/RailAdapter state; reports (RailResultReport) are returned/recorded and state advances only through the authority's command surface. RTN-011's single-writer boundary review must explicitly include the rails surface, and RTN-012's composed journey must show a rail-operation transition executed through the single-writer path. In RTN-012's governed contract update, the authoritative-state-store authority_hosted enumeration may be drafted to name rail-operation records (a deployment-contract text refinement under Contract evolution, not a semantic change).

ACR required?: No — pure interpretation of frozen v0.1 (Area 13's owning-authority text) composed with the deployment topology's single-writer rule. Moving RailOperation lifecycle ownership into the deployment/adapter layer, or letting adapters mutate operation state, WOULD be a semantic change and would require an ACR under spec/architecture-change-requests/; this ruling does neither.

DEP-004 impact: None. DEP-004's reconciliation jobs resolve UNKNOWN by submitting corrective commands through the protocol gateway (components.json, reconciler-workers: "submits corrective commands through the protocol gateway; never mutates authoritative state directly and never reaches rails directly") — exactly the path this ruling mandates. The dispatch gate (RTN-001..011 hard, RTN-012 recommended) is unchanged.

## Q3 — In-process materialization of the component contract

Ruling: In-process materialization inside the existing web-api-boundary application is an acceptable first realization of the 9-component contract, under the DEP-003 precedent, on four conditions: (a) the logical execution topology is realized exactly (one admission point, one authoritative-state writer, adapters behind protocol control) as enforced module boundaries; (b) the externalized process/infrastructure binding remains recorded as future work; (c) the components.json present-set update happens in exactly one governed work item (RTN-012) per topology.md "Contract evolution", with claimed entrypoints that genuinely exist on disk; (d) no production financial effect is reachable from the in-process form (simulated rails, no credentials, fail-closed). Process separation is not required by any frozen text.

Spec grounds:

- spec/durable/execution.md §1 (the precedent, merged as a Git fact at b3bc430, PR #9): "The durable execution substrate is an in-process execution fabric that lives inside the existing web-api-boundary application (no new deployed component; the FUTURE-WORK components in deploy/contracts/components.json remain future work and their present-set is untouched)" — and §1 also states the layering rule that makes in-process hosting safe: "It is NOT, and must never become: a financial authority... The ONLY integration point for execution semantics is handler registration: register(kind, handler). Future protocol authorities plug in there."
- spec/architecture/v0.1/README.md §9: "This directory defines semantics only; it intentionally prescribes no implementation, storage, or service decomposition." — process decomposition is not protocol semantics.
- spec/system-architecture.md, hard boundaries: "Deployment owns: Process topology, persistence infrastructure, queues, schedulers, workers, secrets, runtime configuration..." and "The deployment layer hosts and operationalizes those authorities without duplicating their semantic ownership." — process topology is a deployment-owned decision; layer boundaries are logical ("No layer may ... mutate another layer's authoritative state directly"), enforceable as module boundaries in one process.
- spec/deployment/topology.md, execution topology: "The deployment topology must realize exactly this shape; nothing in this contract may redraw it." — the in-process modules realize the same logical shape; topology.md's as-of-today overlay clause is explicitly interim: "Until their governed work items land, the durable command path, workers, scheduler, persistence, queue, evidence storage and adapters exist only as this contract's requirements. The web/API boundary must not accumulate their responsibilities locally in the meantime" — the RTN wave is the governed work landing those responsibilities as protocol-owned modules (src/lib/protocol-runtime/), not the product/application tier absorbing them; the product surface still hosts no protocol authority.
- spec/deployment/topology.md, Contract evolution: "Adding, removing or re-scoping components, environments or the PAYSWAP_ENV allowlist is a governed change that updates deploy/contracts/components.json, the spec/deployment/* documents and scripts/validate_deployment.py together in one work item." — RTN-012 is exactly that item.
- Honesty rule (same document): "claimed-today entrypoints must exist on disk, and the set of components claiming repository presence today is locked to web-api-boundary until a governed change updates the contract" — and components.json field semantics: "exists_in_repository_today": "True only if the component's entrypoint paths exist in the repository at the declared base SHA." In-process entrypoints (e.g. src/lib/protocol-runtime/gateway/) are repository paths; claiming them is honest, provided the externalized binding remains a future-work marker.
- Isolation: components.json external-rail-adapters production_gate: "Real rails are reachable only with production rail credentials that exist solely in the production secret scope; development, test-ci, sandbox and staging use protocol-owned simulated rails with no external transmission (environments.md F5/F6)"; topology.md simulation rule: "development, test/CI, sandbox and staging use protocol-owned simulated rails — same interface, no external transmission, no real credentials, no signing capability." G7 (registry): "Sandbox/demo can never reach production financial effects without separately authorized production configuration, which they do not hold."

Scope impact: Confirm RTN-010, RTN-011, and RTN-012 as scoped (in-process forms; one governed contract update). Requirements added to RTN-012: per component, record the in-process repository entrypoints that now exist AND the future work that remains (externalized process binding, real-rail credential binding under DEP-005); update topology.md's as-of-today overlay in the same work item; all three validators exit 0; owner stays "deployment" for every component and authority only in protocol-layer entries. Externalization, if ever required for production gates (DEP-008), is deployment-layer binding work from DEP-002 onward — never a protocol change and never a re-scope of this wave.

ACR required?: No — pure interpretation. The frozen architecture prescribes no decomposition (README §9); the component contract is a rank-4 deployment contract evolved through its own documented governed process (Contract evolution), not through an ACR. No v0.1 semantic changes.

DEP-004 impact: None. DEP-004's jobs are themselves in-process background operations on the DEP-003 substrate; the gate (RTN-001..011 hard, RTN-012 recommended) is unchanged. DEP-005 remains where real external transmission binding lands.

## Q4 — Vocabulary mismatch: "identity", "market", "values", "accounting" vs the 24-area registry

Ruling: The deployment contract's and system-architecture's "Protocol owns" enumerations are layer-ownership paraphrases, not area definitions; where a term has no registry area, the conservative mapping holds and no new authority may be invented: "values" → the kernel Money/MoneyBag conventions (core.md §0, GC-1); "accounting" → the A10 Obligation Ledger Authority (the protocol's single financial truth, GC-4) plus the per-area integer arithmetic invariants; "market" → A18 Marketplace Authority (follow-on wave; A03 is the capability-registration surface it feeds); "demand" → A01 (DemandDescriptor/DemandSignal); "identity" → no area and no Identity Authority — identity is subject data owned per-area by each authority's own objects (A01 parties, A03 provider registration, A16 reviewer identity, A19 AgentCredential, A22 FederationMember, A23 AddressOwnershipProof), and the gateway performs per-command subject validation only. The proposal's conservative interpretation is confirmed with this refinement.

Spec grounds: Ruled by precedence — frozen architecture/registry first, deployment contracts third.

- spec/registry/protocol-registry.json: "areaCount": 24, areas A01–A24; no identity area, no market area; A18 owningAuthority "Marketplace Authority" (title "Extensions/Capability Marketplace"), crossReferences A03; A01 primaryObjects include "DemandSignal". Registry consistency: "If any projection disagrees with spec/architecture/v0.1/, that directory prevails."
- spec/architecture/v0.1/core.md §0: "Money: signed integer minor units, 3-letter currency code, explicit decimal scale per currency. No floating point anywhere (GC-1). MoneyBag: set of (currency, integer amount) entries; addition and subtraction are entrywise and deterministic."
- spec/architecture/v0.1/clearing-netting-settlement.md, Area 10: "This ledger is the protocol's financial truth (GC-4); every downstream netting or settlement fact is a projection of it." Owning authority: "Obligation Ledger Authority (protocol layer, area 10) — the single financial authority for debt state (GC-4). No product or deployment component writes or duplicates this ledger."
- deploy/contracts/components.json, protocol-gateway: "protocol authorities per the system architecture hard boundaries — identity, authority, values, accounting, intent, demand, capability, market, liquidity, credit, reservations, routing/compiler, execution admission, clearing, obligations, risk/compliance, recourse, federation — enforced inside a deployment-owned process; the sole admission point for protocol commands" — the text self-declares as a paraphrase ("per the system architecture hard boundaries").
- spec/system-architecture.md, Protocol owns: "Identity, authority, values, accounting, intent, demand, capability, market, liquidity, credit, reservations, routing/compiler, execution, clearing, obligations, netting, risk/compliance, evidence, simulation, extensions, agents, recourse, federation, settlement and finality." — a layer-boundary statement, and itself non-exhaustive/mismatched against the registry in both directions (it omits nothing the registry has, but the registry has no "identity"/"market" areas); system-architecture.md's own header: "Deployment architecture: this document's operational layer; it does not redefine protocol semantics."
- Precedent for conservative interpretation: spec/architecture/v0.1/README.md §9, Known limitations: "Conservative interpretation applied: that file covers areas 13-14; area 15 (evidence) is covered in evidence-risk-compliance.md." — the architecture's own practice for label-vs-content mismatches.

Scope impact: Confirm as-is. RTN-001 (kernel Money/MoneyBag) and RTN-008 (A10 ledger) already carry the "values"/"accounting" weight. RTN-010 implements no identity or market authority — its admission surface validates command schemas (including subject ids) per owning authority and rejects with deterministic reason codes. RTN-012's authority_hosted drafting must stay aligned to registry area/authority names and must not import the paraphrase vocabulary as new authority claims.

ACR required?: No — pure interpretation of the frozen registry/area map against non-normative vocabulary. Materializing an "Identity Authority" or "Market Authority" as a new protocol authority WOULD be a silent semantic change — VOID without an ACR (and a drift-control "duplicate financial authority / undeclared authority" red flag); this ruling forbids that, it does not perform it.

DEP-004 impact: None. No DEP-004 acceptance criterion touches an identity or market surface.

## Q5 — Ownership of product-port re-anchoring, and whether it gates DEP-004

Ruling: Port re-anchoring is product-program work (an additive work item in the product work-item ledger, created through the governed Tech Lead process, owning the src/lib/protocol/ port backings, mock retirement, and the spec/product/*-mapping-records.md re-anchoring); it does NOT gate DEP-004 — DEP-004's dependency is the authorities as runtime code, not the product splice — but it MUST exist and be sequenced with a hard dependency on the merged composed RTN runtime (RTN-012 at minimum), before UI-010's closure acceptance, and before SYS-001's acceptance can pass.

Spec grounds:

- src/lib/protocol/intent-port.ts: "The protocol runtime — and with it the Intent Authority's real state vocabulary — is ARRIVING with the protocol runtime program. When it lands, this port is re-anchored to the runtime and the mock is retired; the surfaces do not change shape." Typed fields: "readonly runtimeStatus: 'ARRIVING'; readonly implementation: 'mock (non-authoritative, presentation-only)'". Same pattern in capability-port.ts ("explicitly NON-AUTHORITATIVE, presentation-only, runtime ARRIVING") and tracking-port.ts ("When the live tracking adapter lands, it is swapped in at getTrackingPort() and ONLY there; no surface or component changes").
- spec/product/intent-mapping-records.md: "The records are re-anchored to the Intent Authority's real state vocabulary when the protocol runtime lands; today the authority-side vocabulary is the **mock's fixture vocabulary** (NON-AUTHORITATIVE, presentation-only), and every record says so."
- Surface ownership: src/lib/protocol/ is a product-owned code surface (the RTN wave's own shared forbidden-surfaces list) — so the RTN wave cannot perform the splice, and the proposal's RTN-010 correctly documents only the command surface the re-anchoring will consume.
- spec/product/work-items.md, invariants: "Changes to this ledger are additive and go through the governed Tech Lead process." — the product ledger (UI-001..UI-010) contains no re-anchoring item today; one must be added additively.
- spec/system-reconciliation.md, reconciliation invariant: "Every consequential product journey must be traceable as: user intent → product interaction → canonical protocol object/state → owning protocol authority → API/runtime boundary → deployment component → durable state/evidence → user-visible outcome. A gap in this chain is a system integration defect, not permission to invent a new authority." — with mock-backed ports the chain breaks at "canonical protocol object/state"; that is a recorded system integration defect, and it is repaired by the re-anchoring item, not by the RTN wave and not by inventing authority.
- spec/system-work-orders/DEP-004.md: "Owned surfaces: background operational jobs and orchestration only"; acceptance: "Jobs consume only authoritative protocol state." — DEP-004 exercises command → gateway → queue → transition → authoritative state/evidence, none of which crosses the product-port seam; the invariant governs "consequential product journeys", and DEP-004's jobs are not product journeys.
- spec/system-work-orders/SYS-001.md: "For each major flow, trace product action → canonical protocol object/state → owning authority → API/runtime boundary → deployment component → durable state/evidence → user-visible outcome." "Depends on: required UI and deployment items merged." — SYS-001 cannot pass while ports are mock-backed; the re-anchoring item becomes one of the "required UI items".
- spec/governance/dogfooding-protocol.md: journeys must exercise "the actual user-visible surfaces where the workflow is user-visible" with "no stubs standing in for financial semantics, no mock authorities, no simulated protocol behavior where real protocol behavior is required" — UI-010's "objective end-to-end workflow evidence" across "the composed system" cannot be mock-backed once the real runtime exists.
- spec/development-state/system-program-state.json (at the proposal's inspected base 0ccb640): "DEP-004 BLOCKED (requires protocol authorities as runtime code — not yet materialized)" — the unblocking condition names the runtime code, not the ports.

Scope impact: No change to the RTN wave itself — no RTN item may touch src/lib/protocol/ or spec/product/ (forbidden surfaces stand). The change is cross-program: at wave activation the Tech Lead opens the additive product-ledger item (port re-anchoring: swap mock backings for runtime adapters over RTN-010's documented command/read surface, retire mocks, re-anchor the mapping records; the port shapes and product surfaces do not change), with hard dependency on the merged composed runtime and sequencing before UI-010 closure acceptance and SYS-001. If UI-010's closure evidence were produced against mocks after the runtime has merged, it would not satisfy the dogfooding standard and closure could not be accepted.

ACR required?: No — pure interpretation and sequencing. The re-anchoring is product-layer work conforming to frozen v0.1 (the ports already disclaim authority; the runtime supplies it); no protocol semantic changes.

DEP-004 impact: None on the dispatch gate. DEP-004 becomes dispatchable after RTN-001..011 merge (hard) with RTN-012 recommended, independent of the port re-anchoring. The re-anchoring item gates SYS-001 (and UI-010 acceptance), not DEP-004; DEP-005/006/007 depend on DEP-004, not on the splice.
